# 魔介表单系统

> 项目周期：2026.03 — 2026.05。本页日期为案例整理日期，不是项目开始时间。

## 业务背景

这是一个面向培训报名、线下活动和付费课程的低代码表单平台，覆盖表单搭建、移动端采集、在线支付、数据管理与活动核销。

不同活动对字段、参与条件和名额有不同要求。平台需要让运营人员配置表单，同时让移动端按照配置完成展示、提交和后续业务操作。

## 我的角色

我独立完成管理后台、移动端 H5 与 NestJS API 的首版架构及核心功能，并使用 Prisma 设计表单、提交记录、支付订单、白名单与核销等数据模型。

## 关键实践

### 从可视化配置到动态表单

基于 Vue 3、Element Plus 与拖拽组件实现可视化编辑器，支持多类型字段、条件联动、唯一性校验、选项名额与高级筛选规则。

建设表单发布、H5 动态渲染和数据提交链路，让后台配置能够用于移动端采集。这里需要关注的不是字段数量，而是字段之间的规则，以及规则对展示和提交的影响。

### 从提交记录到活动管理

实现记录查询、编辑、统计与 Excel/CSV 导入导出，支持白名单、名额控制和核销管理。表单因此不只是一个录入页面，也连接了活动开展后的运营工作。

### 接入支付与微信授权

对接微信支付、支付宝支付及微信网页授权，使用 Redis 管理一次性授权状态与登录票据，并为提交、授权和支付关键流程补充 Jest、Vitest 测试。

技术栈包括 Vue 3、Vite、Element Plus、Vant、Pinia、NestJS、Prisma、PostgreSQL、Redis、JWT 与腾讯云 COS。

## 交付范围

平台支持运营侧搭建与发布表单、用户侧采集与支付，以及提交后的数据管理和活动核销。本页暂不公开累计提交量、交易金额、用户数据与内部截图。

## 后续复盘方向

以下是准备进一步整理的技术问题，不是已发表的结论：

- 条件联动、唯一性与名额限制，如何划分前端体验和服务端校验的责任？
- 表单配置与提交数据之间，如何设计清晰的数据模型？
- 授权、支付与提交链路，哪些失败场景需要单独验证？
